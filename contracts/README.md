# Veyrion Public Contract Registry

Versioned JSON Schemas for API, domain, and Worker/runtime contracts.
Consumers (Java DTO, TypeScript parser, fixtures) must stay aligned via
`SchemaContractAcceptanceTest`. Field-constant stubs for Finding /
SecurityHypothesis / CoverageMatrix are generated by
`scripts/generate-contract-types.ps1` into `frontend/src/generated/contracts.ts`
(required/properties only; not a full wire parser).

## Layout

```text
contracts/
  schemas/
    api/finding.v1.json
    domain/security-hypothesis.v1.json
    domain/coverage-matrix.v1.json   # aligned with domain.coverage.CoverageMatrix
    domain/evidence-graph.v1.json    # aligned with domain.ir.EvidenceGraph (P1-02)
    analyzer/capability-negotiation.v1.json  # P1-07 Analyzer handshake
    analyzer/ir-chunk.v1.json                # P1-07 IR staging chunk
    analyzer/analyzer-result.v1.json         # P1-07 terminal result + manifest
    runtime/run-profile.v1.json              # P1-07 server-fixed RuntimeAdapter profile
    worker/runtime-observation.v1.json
  fixtures/                 # acceptance fixtures
  architecture-baseline.txt # known domain import-rule exceptions
  migration-checksums.txt   # pinned SHA-256 of applied V00x SQL files
```

Existing Worker JSON Schemas under `src/main/resources/schemas/` remain
in force for Worker task/lease/trace wire formats; new neutral contracts
land here first and may later be mirrored into resources.

## Compatibility matrix

| Change | Rule |
|--------|------|
| Add optional field | Compatible within same major (`*.v1`) |
| Add required field | Breaking — bump to `*.v2` or dual-read |
| Remove / rename field | Breaking |
| Tighten enum (remove value) | Breaking |
| Add enum value | Compatible if consumers treat unknown as degrade |
| New `extensions.*` / `x-veyrion-*` | Compatible; ignored by strict core validation |

Major version is the filename suffix (`finding.v1.json`). Do not rewrite an
already-published schema file in place for breaking changes.

## Unknown kind

- Closed enums that affect security gates (`verificationStatus`, Worker
  `requiredCapability`, network mode) **reject** unknown values.
- Open taxonomy fields (`family`, `securityProperty`, observation `kind`)
  **accept** unknown strings and project them to a documented fallback
  (e.g. `UNKNOWN`) without elevating verification status.
- Fixtures and consumer tests must cover both paths.

## Namespaced extensions

Producers may attach language- or framework-specific payload only under:

- `extensions.<namespace>.*` (preferred object bag), or
- top-level `x-veyrion-<name>` keys.

Core validators with `additionalProperties: false` must still allow these
two patterns. Extensions cannot become FACT, change authorization, or
upgrade verification status.
